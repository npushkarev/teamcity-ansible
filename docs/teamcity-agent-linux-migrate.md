# Перенос Linux-агента TeamCity на новый сервер (Debian 12)

Скрипт `scripts/teamcity-agent-linux-migrate.sh` ставит **нового** агента рядом со старым: свой каталог `/opt/buildAgent2026`, своя служба systemd `teamcity-agent2026`, Java 21 из пакета `teamcity-agent-jdk21` (`/opt/teamcity-agent-jdk21`). Он переносит параметры `system.*`/`env.*` старого агента, по которым сборки выбирают агента. Затем, когда на старом агенте нет сборки, штатно останавливает его и выключает его автозапуск.

Каталог и настройки старого агента не меняются и не удаляются: его можно вернуть командами, которые печатает скрипт. Если новый агент не запустился или не зарегистрировался на сервере, скрипт сам возвращает старого.

## Что положить рядом со скриптом

1. `teamcity-agent-linux-migrate.sh` из этого репозитория. Каждый из трёх скриптов работает сам по себе, остальные можно не копировать.
2. `buildAgentFull.zip` с **нового** TeamCity: **Agents → Install Build Agents → Zip file distribution**. Скрипт ищет `buildAgent*.zip` рядом с собой, в текущем каталоге и в `~/Downloads` того, кто запустил `sudo`. Если архива нет, скрипт скачает `http://172.17.6.61:8111/update/buildAgentFull.zip` с нового сервера. Для этого нужен curl, wget или python3. Архив агента другой версии (например, `buildAgent.zip` со старого сервера, сборка 58658) скрипт не берёт: нужен агент 2026.x.
3. Java 21, если она ещё не установлена: `teamcity-agent-jdk21_21.0.12.12.1-1_amd64.deb` из `files/teamcity-agent-jdk21/debian12-amd64`, а на Debian 9–11 (`libc6` старше 2.36) — `teamcity-agent-jdk21_21.0.12.12.1-1~deb9_amd64.deb` из `files/teamcity-agent-jdk21/debian9-amd64`. Внутри одна и та же Java, отличаются только зависимости пакета; не тот пакет скрипт не ставит и пишет, какой нужен (скачайте кнопкой **Download** в GitLab, не указатель LFS). Скрипт сам установит его командой `dpkg -i`, больше ничего не меняя. Подробнее о пакете: [teamcity-agent-jdk21-debian12.md](teamcity-agent-jdk21-debian12.md).

Найденные `.deb` и `.zip` скрипт берёт, только если файл и его каталог принадлежат root или вам и их не может изменить другой пользователь. Остальные он пропускает и пишет об этом: `.deb` устанавливается от root.

## Запуск

```bash
sudo bash teamcity-agent-linux-migrate.sh --check
sudo bash teamcity-agent-linux-migrate.sh
```

`--check` только показывает, чего не хватает, и план. Без него скрипт спрашивает `Выполнить? [Y/n]`: Enter или `y` — да. Если терминала нет (запуск из другого скрипта), добавьте `--yes`.

Скрипт показывает:

- **Проверка: чего не хватает**:
  - старый агент: каталог, `serverUrl`, `name`, запущен ли, от какого пользователя и на какой Java, как запущен и что запускает его при загрузке, идёт ли на нём сборка;
  - доступность нового сервера, Java 21, дистрибутив;
  - каталог и служба нового агента, другие агенты на машине, группа `docker`;
  - параметры старого агента: какие добавятся, какие отличаются, какие не переносятся; его переменные окружения;
- **Что будет сделано** — нумерованный план;
- **Что сделано** — каждый шаг с проверкой;
- **Итог** — что сделать в TeamCity и команды возврата старого агента.

## Порядок и безопасность

1. Пока старый агент работает, скрипт ставит нового:
   - Java (если нужно);
   - распаковка в новый каталог;
   - настройки (`serverUrl`, `name`, параметры старого агента — с проверкой после записи);
   - рабочие папки — как у старого агента, если они вне его каталога (`workDir=/data/work`, `tempDir=/data/temp`, `systemDir=/data/system` на отдельном диске): там место, которое нужно сборкам (требование «Free disk space»), и очистка работает так же. Недостающие папки создаются от пользователя агента. Папки внутри каталога старого агента (`../work`) не берутся — у нового свои. С `--keep-old` оба агента работают одновременно, поэтому папки не делятся. Если агент уже перенесён, повторный запуск пропишет папки и перезапустит его после текущей сборки;
   - владелец каталога;
   - служба systemd: создаётся и включается, но ещё не запускается.
2. Только потом старый агент останавливается **штатно**: его собственной командой `agent.sh stop`, от его пользователя и с его Java.
   - Команду `agent.sh stop` отменить нельзя: агент выйдет после сборки, что бы ни случилось дальше. Поэтому, если на агенте идёт сборка, скрипт сначала ждёт её окончания (до `--wait` секунд, 600) и только потом отправляет команду.
   - Сборку скрипт узнаёт двумя способами. Первый — процессы под JVM агента (шаги сборки, Ant, Maven, docker). Второй — журнал агента `logs/teamcity-agent.log`: строка `Starting Build {id=…}`, после которой ещё нет `Build finished, build id …`. Так видны и этапы, когда агент работает сам, без отдельных процессов: получение исходников с сервера (server-side checkout), загрузка зависимостей-артефактов, публикация артефактов, переход между шагами. Команда уходит, только если две проверки подряд (через 2–4 с) не видят сборки.
   - Если сборка не закончилась за это время, скрипт выходит с кодом 3. Он ничего не отправлял старому агенту, его автозапуск не выключен. Новый агент остаётся таким, каким был до запуска скрипта. Если скрипт его только что поставил, он не запущен и его служба выключена. Если он был запущен вручную, скрипт запускает его снова так же. В итоге скрипт пишет, в каком состоянии новый агент. Запустите скрипт снова после сборки: он продолжит с этого места.
   - Если сборка пришла на агента в те несколько секунд между последней проверкой и командой, агент доделает её и выйдет. Тогда скрипт запускает нового агента рядом, на его порту.
   - Если в журнале агента осталась строка начала сборки без строки конца (журнал правили вручную, или агент не смог начать сборку — тогда после неё в журнале строка `Failed to start build on agent`), скрипт считает, что сборка идёт, и после `--wait` выходит с кодом 3. Проверьте в TeamCity, что сборки на агенте нет, и запустите с `--force`.
   - С `--force` сборка прерывается (`agent.sh stop force`, затем TERM/KILL), если не закончилась за `--wait` секунд.
3. Автозапуск старого агента выключается:
   - служба systemd или init-скрипт SysV, которые запускают `agent.sh` из его каталога, — `systemctl disable`. Это и экземпляр шаблона (`teamcity-agent@buildAgent` с `ExecStart=/opt/%i/bin/agent.sh`), и служба, которая запускает агента через свой скрипт-обёртку. Службы, которые только упоминают каталог (например, резервное копирование), скрипт показывает и не трогает;
   - строки cron и `/etc/rc.local`, которые запускают `agent.sh` из его каталога, сами или через скрипт-обёртку (`@reboot /home/teamcity/start-agent.sh`), — комментируются (`#tcagent-off# `). Копия файла сохраняется в `/var/backups/teamcity-agent-linux/`;
   - каталог узнаётся и через символическую ссылку: если `/opt/buildAgent` — ссылка на `/srv/buildAgent`, найдутся строки с обоими путями;
   - если служба, в которой работает старый агент, запускает `agent.sh` по относительному пути (как init-скрипт из примера JetBrains: `cd BuildAgent/bin; ./agent.sh start`), она считается автозапуском этого агента.

   Что скрипт сам не выключает, он показывает с `[НЕТ]` и не продолжает. Выключите это вручную и запустите скрипт снова (или используйте `--keep-old`):
   - строка cron или `/etc/rc.local`, которая запускает сразу двух агентов;
   - автозапуск через supervisor или пользовательскую службу systemd;
   - автозапуск `agent.sh`, каталог которого не определить (относительный путь, переменные), если другого автозапуска у старого агента не найдено. Если найден, такие записи показываются как `[ВНИМ]`;
   - агент запущен из cron или `/etc/rc.local`, но строка не найдена.
4. Скрипт запускает `teamcity-agent2026` и проверяет:
   - агент работает от нужного пользователя;
   - на Java из `/opt/teamcity-agent-jdk21`;
   - зарегистрировался на сервере (`logs/teamcity-agent.log`).
5. Если на шагах 2–4 что-то не вышло (или скрипт прервали, `Ctrl+C`), он сам всё возвращает:
   - выключает новую службу;
   - включает автозапуск старого агента как было;
   - запускает старого агента так, как он был запущен: службой или вручную, с прежним окружением.

   Если старый агент уже получил `agent.sh stop` и ещё доделывает сборку, запустить его сразу нельзя. Скрипт пишет об этом `[НЕТ]` и печатает команду, которой его запустить после окончания сборки.

Старого агента скрипт не останавливает через `systemctl stop`. В юните по примеру JetBrains `ExecStop=agent.sh stop` только просит агента остановиться, а systemd сразу завершает все его процессы, и сборка прерывается. Поэтому скрипт поступает так:

1. Добавляет службе старого агента временную настройку `/run/systemd/system/<служба>.d/50-teamcity-agent-linux.conf`: без `ExecStop` и без `Restart`.
2. Штатно останавливает агента.
3. Только после этого делает `systemctl stop` и сразу убирает временную настройку. Она остаётся, только пока агент доделывает сборку (скрипт печатает, как её убрать), и в любом случае пропадает после перезагрузки.

`agent.sh stop` отправляется только агенту, который точно работает из этого каталога и слушает порт из своего `logs/buildAgent.xmlRpcPort`. Иначе `agent.sh stop` уходит на порт 9090 и останавливает другого агента (проверено: старый и новый так останавливают друг друга).

Агенты TeamCity в контейнерах (процессы в другом пространстве имён монтирования) скрипт показывает одной строкой и не трогает. Каталоги внутри контейнера не путаются с каталогами машины.

Значения параметров и переменных окружения скрипт печатает с маскировкой. Значения ключей с `pass`, `pwd`, `token`, `secret`, `key`, `credential`, `auth` скрываются целиком. В остальных скрываются пароли в URL (`https://<скрыто>@nexus/...`), после `password=` и длинные шестнадцатеричные строки.

## Пользователь, права, Docker

Новый агент работает от того же Linux-пользователя, что и старый; пароль не нужен.

- От root агент не запускается. Если старый агент работает от root, укажите пользователя: `--user <имя>`.
- Скрипт отдаёт этому пользователю только каталог нового агента (`chown -R`). Каталог старого агента, домашние каталоги и другие каталоги не меняются.
- Если на машине есть Docker, а пользователь не в группе `docker`, скрипт предупреждает. Добавляет пользователя администратор сам: `sudo usermod -aG docker <пользователь>`. Это даёт права root через Docker, решите осознанно.

У службы systemd не будет переменных окружения старого агента. Например, `JAVA_HOME`, если старого агента запускали из входа пользователя. Скрипт показывает такие переменные. Если они нужны сборкам, допишите их в `buildAgent.properties` нового агента как `env.ИМЯ=значение`.

## Если новый агент уже распакован вручную

Так на ba-deb12-01: в `/opt/buildAgent2026` уже лежит агент 2026.2 с `serverUrl` нового сервера, своим именем и авторизацией. Скрипт берёт его как есть:

- не распаковывает заново;
- не меняет `serverUrl`, `name` и токен, поэтому авторизация и пул в TeamCity сохраняются;
- добавляет только недостающие параметры старого агента, с резервной копией `buildAgent.properties.bak-*`;
- закрывает `buildAgent.properties` от других пользователей (`chmod 600`): в нём токен агента. Так же закрываются копии `conf/buildAgent.properties*` (например, старые резервные копии `teamcity-agent-copy-settings.sh`): в них тоже может быть токен. Символические ссылки скрипт не трогает;
- если этот агент запущен вручную, штатно останавливает его, когда на нём нет сборки, а потом запускает уже через службу.

Если на новом агенте сборка идёт дольше `--wait`, скрипт выходит с кодом 3. Он ничего не отправляет агенту и больше ничего не меняет. Запустите его снова, когда сборка закончится.

Если в каталоге нового агента есть символические ссылки (например, `conf` ведёт в `/home/user/conf`), скрипт его не берёт: настройки записались бы в чужой каталог.

Копии агента в других каталогах скрипт не трогает (например, в домашнем каталоге `/home/user` с тем же токеном). Если копия запущена, он попросит её остановить и напечатает команду. Если не запущена — предупредит, что запускать её вместе с новым нельзя.

Повторный запуск безопасен: сделанное он пропускает. Если всё уже сделано, скрипт пишет «Ничего делать не нужно: перенос уже выполнен» и ничего не меняет.

## Служба нового агента

`/etc/systemd/system/teamcity-agent2026.service`, первая строка — `# Created by teamcity-agent-linux-migrate.sh`:

- основа — пример JetBrains: `Type=oneshot`, `RemainAfterExit=yes`, `SuccessExitStatus=0 143`. Так служба переживает самообновление агента;
- `User=`/`Group=` — пользователь старого агента;
- `Environment=TEAMCITY_JRE=/opt/teamcity-agent-jdk21`: Java 21 для запуска и остановки;
- `conf/buildAgent.properties` нового агента — с правами `600` и владельцем-пользователем агента: туда агент пишет свой токен;
- `ExecStop` ждёт окончания текущей сборки (до 10 минут, потом systemd её прерывает) и ничего не отправляет, если агент из этого каталога не запущен.

```bash
sudo systemctl status teamcity-agent2026
sudo journalctl -u teamcity-agent2026
sudo systemctl restart teamcity-agent2026   # ждёт окончания текущей сборки (до 10 минут)
```

Журналы агента — `/opt/buildAgent2026/logs/teamcity-agent.log` и `launcher.log`. Если агента остановили вручную (`agent.sh stop`), служба остаётся в состоянии `active (exited)`: запускайте `systemctl restart`, а не `start`. Не запускайте второй экземпляр через `agent.sh start`.

После переноса в новом TeamCity: **Agents → Unauthorized → агент → Authorize**, затем назначьте пул. Агента, который уже был авторизован, только проверьте.

## Выключить старого агента отдельно

`scripts/teamcity-agent-linux-disable-old.sh` делает тот же штатный останов и выключение автозапуска, что и перенос, но без установки нового агента (например, после переноса с `--keep-old`). Каталог и настройки старого агента, а также новый агент не трогаются.

Скрипт отказывается, если указанный каталог на самом деле новый агент:

- совпадает с `--new-dir` или вложен в него;
- совпадает с каталогом службы `--service`;
- в нём метка нового агента;
- в нём `serverUrl` нового сервера;
- в нём агент 2026.x (файл `BUILD_*` с номером от 200000; у старого агента 2018.1.3 — `BUILD_58658`).

Остановка и автозапуск — те же, что при переносе: команда `agent.sh stop` уходит, только когда на агенте нет сборки. В конце скрипт печатает команды, которые включают старого агента обратно. При повторном запуске пишет «Старый агент уже выключен» и повторяет эти команды.

```bash
sudo bash teamcity-agent-linux-disable-old.sh --check
sudo bash teamcity-agent-linux-disable-old.sh
```

Если сборка не закончилась за `--wait` секунд, скрипт выходит с кодом 3 и ничего не меняет: агент работает, автозапуск включён. Запустите скрипт ещё раз после сборки или с `--force`.

## Удалить нового агента и поставить заново

`scripts/teamcity-agent-linux-remove-new.sh` штатно останавливает нового агента, удаляет службу `teamcity-agent2026` и каталог `/opt/buildAgent2026`. Пока не пройдут все проверки, он ничего не меняет:

- в пути нет символических ссылок (и `/opt/ссылка//` тоже); каталог — не `/`, не каталог верхнего уровня (`/opt`, `/home`, ...), не точка монтирования; не домашний каталог пользователя и не содержит его;
- каталог не совпадает со старым агентом (`--old-dir`), не лежит внутри него и не содержит его. Так же — с каталогом любого другого агента: запущенного, найденного на диске или того, который запускают служба, init-скрипт, cron или `/etc/rc.local`;
- в каталоге только файлы агента: то, что есть в дистрибутиве, и то, что создаёт сам агент (`bin`, `conf`, `lib`, `logs`, `work`, `temp`, `system`, `plugins`, `tools`, ...);
- каталог не похож на старого агента, что бы ни было указано в параметрах: агент в нём не старой версии (`BUILD_*` от 200000), не работает на Java ниже 17, метка нового агента не называет его старым, а его строки автозапуска не выключены скриптами переноса (`#tcagent-off#`);
- есть метка `.teamcity-agent-linux-migrate` (её пишет скрипт переноса) или `conf/buildAgent.properties` с `serverUrl` нового сервера и файлом `BUILD_*`. При этом `serverUrl` и токен не такие, как у старого агента;
- службу `teamcity-agent2026` скрипт удаляет, только если её создал скрипт переноса для этого каталога или её `ExecStart` запускает агента именно оттуда. Если каталог упоминают другие службы, cron или rc.local, скрипт отказывается.

При отказе скрипт показывает причину. Если каталог может быть новым агентом, но не прошёл проверку (нет метки, посторонние файлы), скрипт печатает команду для удаления вручную — решать вам. `systemctl disable --now` в этой команде есть, только если служба запускает агента именно из этого каталога. Для каталога, похожего на старого агента, и для агента другого сервера такая команда не печатается.

Если на новом агенте идёт сборка, скрипт ждёт её окончания (до `--wait` секунд) и только потом отправляет `agent.sh stop`. Сборку он узнаёт так же, как при переносе: по процессам и по журналу агента. Если сборка не закончилась за это время, скрипт выходит с кодом 3 и ничего не меняет. С `--force` он прерывает сборку, если она не закончилась за `--wait` секунд. Оставшиеся в каталоге процессы пользователя агента завершаются только с `--force` (TERM, затем KILL); процессы других пользователей не трогаются.

Каталог удаляется командой `rm -rf --one-file-system`, после чего скрипт проверяет, что его нет. Старого агента скрипт не включает: если тот выключен, печатает команду, как его вернуть.

```bash
sudo bash teamcity-agent-linux-remove-new.sh --check
sudo bash teamcity-agent-linux-remove-new.sh
```

Если новый агент успел зарегистрироваться, удалите его в новом TeamCity: **Agents → агент → Remove**.

## Коды выхода

| Код | Значение |
|---|---|
| 0 | сделано или делать нечего, `--check` без замечаний, отмена на вопросе |
| 1 | ошибка во время выполнения (при переносе — уже после автоматического возврата старого агента) |
| 2 | есть пункты `[НЕТ]`, ничего не изменено |
| 3 | идёт сборка дольше `--wait`, ничего не прервано. Агенту не отправлено `agent.sh stop`, автозапуск не выключен. Исключение — сборка пришла на агента в несколько секунд между последней проверкой и командой: тогда агент выйдет после неё |

## Проверено

Синтаксис (`bash -n`) и shellcheck 0.10.0 — без ошибок и предупреждений (`-S warning`); остаются только замечания уровня info/style.

**Сквозные тесты** — 60 сценариев, все проходят (последний полный прогон — на версии с распознаванием сборки по журналу агента):

- **Где:** контейнеры Debian 12 (amd64, systemd 252) на изолированной сети Docker (`--internal`, без интернета).
- **Новый сервер:** стандартный образ `jetbrains/teamcity-server:2026.2`. Регистрация, авторизация и параметры агента проверялись через REST API, настоящие сборки (shell и Ant) шли на агентах.
- **Старый агент:** настоящий агент 2018.1.3 на Java 8, его сервер — простой HTTP-сервер. Для сценариев «сборка на старом агенте» классы его JVM заменены программой с тем же расположением процессов. Её запускает настоящий `agent.sh`, она пишет файлы порта и PID, строки начала и конца сборки в журнал (как настоящий агент) и ведёт себя при `stop` и `stop force` так же. Сборка у неё бывает трёх видов: процесс `sh`, Ant-процесс `java` и этап без процессов (работает только JVM агента).
- **Новый агент:** настоящий `.deb` с JDK 21 и настоящий `buildAgentFull.zip` 2026.2.

Проверены:

- **Установка:** `.deb` и архив рядом со скриптом; архив скачивается с сервера (curl, wget); распаковка через unzip, python3 и `jar` из JDK; архив старого сервера и `.deb`, подложенный другим пользователем, не берутся.
- **Как запущен старый агент:**
  - юнит по примеру JetBrains и экземпляр шаблона (`/opt/%i`);
  - init-скрипт SysV, с абсолютным и с относительным путём;
  - cron, напрямую и через скрипт-обёртку;
  - `/etc/rc.local`;
  - `Type=simple` с `Restart=always`;
  - вручную, в том числе с многострочной переменной окружения;
  - каталог через символическую ссылку (cron и юнит; агент запущен и остановлен);
  - от root (нужен `--user`).

  Каждый раз проверена перезагрузка: старый агент больше не запускается, новый запускается.
- **Сборки:**
  - сборка на старом агенте дольше `--wait`: выход 3, команда остановки не отправлена, автозапуск не тронут, сборка не прервана;
  - `Ctrl+C`, пока скрипт ждёт сборку: старый агент не тронут;
  - сборка, которая дольше `--wait` и при этом новый агент не запускается;
  - `--force`; Ant-процесс `java` считается сборкой, а не агентом;
  - этап сборки без процессов (как получение исходников с сервера): `migrate` и `disable-old` видят сборку по журналу агента, не отправляют `agent.sh stop` до её конца, выходят с кодом 3 или дожидаются её;
  - на настоящем агенте 2026.2 сборка видна и по журналу (`Starting Build {id=…}` без `Build finished`);
  - сборка, оборванная падением агента (`kill -9`), после его перезапуска сборкой не считается (строка `Build agent started`) — на подмене 2018.1.3 и на настоящем 2026.2;
  - `remove-new` во время сборки на новом агенте: ждёт её до `--wait`, потом удаляет агента; с коротким `--wait` выходит с кодом 3, ничего не меняя;
  - выход 3 при переносе: итог правильно говорит, в каком состоянии новый агент (не запущен; снова запущен вручную; работает через службу, которая уже была включена);
  - `systemctl stop` нового агента ждёт окончания сборки.
- **Автоматический возврат:**
  - новый агент не запустился или не зарегистрировался;
  - скрипт получил SIGTERM;
  - напечатанные команды возврата и удаления тоже работают.
- **Принятие нового агента:**
  - уже распакованного и запущенного вручную, в том числе со сборкой на нём;
  - копии `buildAgent.properties*`, которые могут читать другие пользователи, закрываются (`600`), символическая ссылка не трогается;
  - копия агента в `/home/user`;
  - `--keep-old`, свои `--new-dir`/`--service`, повторные запуски ничего не меняют.
- **Отказы:**
  - `remove-new`: старый агент, даже при неверных `--old-dir` и `--server`; домашний каталог; `/opt`; путь через символическую ссылку (и с `//`); посторонние файлы; копия без метки;
  - `disable-old`: каталог нового агента;
  - строка cron, которая запускает двух агентов;
  - агент в другом пространстве имён монтирования не принимается за агента машины.
- **Секреты:** в выводе скриптов нет токенов и паролей, в том числе внутри URL и строк подключения. После регистрации агент сам записал токен в `buildAgent.properties`, права остались `600`.
- **copy-settings.sh:** перезапуск нового агента без системной Java и во время Ant-сборки; его резервные копии — с правами `600`.

Не проверено:

- **настоящая сборка на агенте 2018.1.3:** сервера 2018.1.3 в тесте нет. Что агент 2018.1.3 пишет в журнал те же строки начала и конца сборки (`Starting Build {id=…}`, `Build finished, build id …`, `Build agent started`), проверено по его `lib/agent.jar` (класс `BuildAgentImpl`). На 2026.2 — настоящей сборкой.
- **получение исходников с сервера на настоящем агенте:** этап без процессов проверен на подменённом старом агенте, который пишет в журнал те же строки.
- **ba-deb12-01:** на нём скрипты ещё не запускались. Начните с `--check`.
- **copy-settings без файла порта:** отказ `copy-settings.sh` отправлять `agent.sh stop`, когда нет `logs/buildAgent.xmlRpcPort`, проверен только чтением кода. В тесте агент после изменения `buildAgent.properties` сам перезапускался и успевал записать файл порта.
